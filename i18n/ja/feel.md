# feel.md — モーションが本物に読める条件

このファイルは API の話ではない。*なぜそのアニメーションが嘘くさく見えるのか*の話だ。

並び順は、その問題がどれだけ深く錯覚を壊すかにおおむね従っている。**先に出てくるものから直すこと。
後ろの細部が効いてくるのは、前が正しくなってからだ。**

ここに書かれているものはすべて `SKILL.md` §1 の仕様語彙で書かれている。プラットフォーム固有の
話は 1 つもない。

---

## 0. ひとことで言う原則

> アニメーションは、**考えさせずに**何が起きたかを伝えるものであるべきだ。
> ユーザーはアニメーションに気づくべきではない。気づくべきなのは *あれはそこから来た* という事実だ。

人が立ち止まって*見とれる*アニメーションは、プロダクトにおいてはほぼ例外なく長すぎる。

---

## 1. パラメータは、動く値の種類に選ばせる

何を使うか迷ったら、**でっち上げてはいけない**。*どんな種類の値が動いているか*で選べば、
答えはもう決まっている。

| 何をアニメーションさせるか | 使うもの |
|---|---|
| キーフレームが 3 つ以上 | トゥイーン、`dur 0.8`、curve `inout` |
| 位置と回転 — `x` `y` `z` `rotate` `skew` | `spring(0.28, 0.2)` — わずかなオーバーシュート |
| スケール系 | `spring(0.27, 0)` — **オーバーシュートなし** |
| その他すべて — 不透明度、色、ブラー、フィルタ | トゥイーン、`dur 0.3`、curve `out` |

最後の行のカーブは、正確に名指ししておく価値がある。プラットフォーム既定より**浅い easeOut** だ。
立ち上がりが唐突でなく、終わりの柔らかさは同じ。cubic-Bézier で言えば `(0.25, 0.1, 0.35, 1)`。
名前付きカーブしかないランタイムなら、"quint out" ではなく "sine out" か "quad out"。

**この表からそのまま読み取れる結論が 3 つある：**

1. 空間を占めるもの（位置、サイズ）→ スプリング。占めないもの（不透明度、色）→ トゥイーン。
2. 拡大と縮小は**弾ませてはいけない**。移動は弾んでよい。
3. 既定の持続時間はたった `0.3s`。それより長くするなら理由が要る。

---

## 2. スプリングの本当の価値は速度の引き継ぎであって、弾み具合ではない

たいていの人はスプリング＝弾むもの、と思っている。違う。いちばん重要な性質は、**アニメーションが
割り込まれたとき、現在位置から現在の速度で続く**ことだ。ぴたりと止まってやり直すのではなく。

これが *オブジェクトのように感じる* と *スライドショーのように感じる* を分ける線だ。

どちらのアニメーションも完了しないうちに 2 つの目標値のあいだをトグルされる値を考えよう。

- **トゥイーン**はトグルのたびにハードリスタートする。再スタートは常に速度ゼロから始まるので、
  ユーザーが操作したまさにその瞬間——いちばん見られている瞬間——に動きが目に見えて引っかかる。
- 目標値が動いた**スプリング**は位置と速度を保つ。反転が、慣性のあるものを押し返す感触になる。
  積分がやっているのは文字どおりそれだからだ。

**判定基準：このアニメーションはユーザーの直接操作で始まるか？**

| トリガー | 使うもの | 理由 |
|---|---|---|
| ドラッグ、スワイプ、ジェスチャー、カーソル追従 | **スプリング**（必須） | 引き継ぐべき実際の速度がある |
| クリック／ホバーによる移動やスケール | **スプリング** | 何度も割り込まれ得る |
| トグルによるレイアウト変化 | **スプリング** | 同上 |
| 出現／退出のフェード | **トゥイーン** | 引き継ぐ速度がない。制御できるタイミングのほうが重要 |
| 時間軸を合わせる必要があるもの（stagger、シーケンス、動画） | **トゥイーン** | スプリングには信頼できる終了時刻がない |
| スクロール連動 | 直接バインドしてから平滑化 | §7 を参照 |

**Tier 2** のランタイム（`SKILL.md` §2）でも割り込みはできるが、速度は失われる。緩和策は 2 つ、
優先順に：実際にジェスチャー駆動である少数のインタラクションについてはスプリングを自前で積分する
（`spring.md` §3 — 15 行で済む）。それ以外はすべて、割り込まれた瞬間の**現在**値を読み取って
そこから `b ≤ 0.15` でアニメーションさせる。これなら再スタートが引っかかりとして読まれない程度に
小さく収まる。

**Tier 3** では抗わないこと。再トリガーされ得るアニメーションは `dur ≤ 0.2s` に保つ。その閾値の
下ではハードリスタートは知覚の下限を下回り、誰にも見えない。

## 3. `Dv` と `b` で調整する。生の係数は決して触らない

`stiffness: 400, damping: 32` を思い描ける人はいないし、2 つのつまみは相互作用する——だから
「もう少し速く」が設計のやり直しになる。視覚的持続時間とバウンスで作業し、変換は境界で一度だけ行う。

完全な変換式、各バウンス値が実際に生むオーバーシュート量、そして積分器 → `references/spring.md`。

要点だけ：

- `b` は *どれだけオーバーシュートするか*。`0.15` は目標値を約 0.6% 超え、`0.4` は約 9.5% 超える。
- `Dv` は *どれだけ長く見えるか*。尾はそのあとに起きる。だからこそスプリングとトゥイーンを
  同じ土俵で並べられる。
- スケールは常に `b = 0`。
- プロダクトごとに `b` は 1 つ。バウンス値の混在は、口をきいたことのない複数人が組み立てた
  インターフェースの、いちばん分かりやすい兆候だ。

## 4. 因果関係：ものは、来たところから来る

これを破ったら、カーブをどれだけ磨いても救えない。

- ドロップダウンは**それを開いたコントロールから**展開する。画面中央からフェードインするのでは
  ない。transform origin（またはアンカーポイント）をコントロール側に置く。
- モーダルはクリックされたカードから育つ。ある要素を別の要素の位置へアニメーションできる
  ランタイムならそうする。できないなら、せめてカードの位置とサイズからモーダルを開始して
  動かすこと。フェードではなく。
- サイドバーは**自分の側**からスライドインする。下からではない。
- リスト項目を削除したら、残りは**空いた隙間を詰める**。飛ぶのではなく。
- トーストは、最終的に落ち着く角から入ってくる。

**共有要素の一般的な手順**。組み込みの仕組みを持たないランタイムでの話だ：

```
1. 変化の前に、始点の矩形を計測する          （位置、サイズ）
2. レイアウト変化はそのまま即座に起こさせる
3. 終点の矩形を計測する
4. 逆変換をかけて、見た目上は始点の位置に戻す
5. その変換を単位変換までアニメーションさせる
```

動くのは transform だけなので、レイアウトアニメーションに見えてもコンポジットで安く済む。
矩形を計測して transform をかけられるランタイムならどれでも動く——つまり全部だ。

**travel の距離感：** マイクロインタラクションは `4–12px`、コンポーネント遷移は `16–40px`、
パーセント指定は全画面規模の移動だけ。

`y: 100` からフェードインさせるのはいちばんよくある間違いだ。ツールチップにとってその距離は
*別の部屋から到着した*と読まれる。

## 5. 出現と退出の非対称性

| | 出現 | 退出 |
|---|---|---|
| 持続時間 | `0.2 – 0.35s` | 出現の **0.5 – 0.7×** |
| カーブ | `out` / スプリング | `in` |
| 距離 | フル | **半分以下** |
| 開始スケール | `0.95`（`0` ではない） | `0.98`（ほとんど縮まない） |

理由：出現時、ユーザーは新しい情報を*捕まえ*なければならず、それを見つけるのに時間が要る。
退出時、そのものはすでに本人にとって無関係で、待たせるのは時間の無駄でしかない。

出現の `out` と退出の `in` は、体験全体としては `inout` に合成される。

`scale: 0` から出現させてはいけない。それは *無から存在へ* という意味だが、UI 要素はほぼ常に
*どこか別の場所から* 来る。「現れた」と言うには `0.95` で十分だ。

**機構が要るのは退出のほうだ。** 出現のアニメーションは簡単だ——ものは存在しているのだから、
動かせばいい。退出は、論理的には削除済みのものを生かしておく必要がある。ランタイムごとに解法が
違い、「退出アニメーションが再生されない」の原因第 1 位でもある。退出を設計する*前*に、
自分のアダプタでその機構を見つけておくこと。あとからではない。

## 6. オーケストレーション：stagger は装飾ではなくリズムだ

10 個が同時に現れれば、1 つの塊として読まれる。ずらせば順序が生まれ、方向が生まれる。

**間隔の選び方：**

| 項目数 | 間隔 | 合計の予算 |
|---|---|---|
| 3–6（メニュー、カード列） | `0.04 – 0.06s` | ≤ 0.35s |
| 7–15（リスト） | `0.02 – 0.04s` | ≤ 0.5s |
| 文字ごと | `0.02 – 0.03s` | 長さ次第。1s を超えるなら単語単位に切り替える |
| 20 超 | 個別に stagger しない | グループ化するか、全体をフェードする |

**合計は絶対の上限だ。** 20 項目に `0.1s` の stagger をかければ 2 秒になる。最後の 1 つが着地する
ころには、ユーザーは別のことをしている。書く前に算数をすること。

**方向には意味を持たせる：**
- **先頭から** — 上から下、読み順に合う、安全な選択
- **末尾から** — 折りたたみ用。巻き戻るように見える
- **中央から** — 外へ開く。儀式的で、ヒーローに向く
- **ユーザーがいま触れた項目から** — 外へ放射する ← **使える中でいちばん強い因果の表明**であり、
  ほとんど誰も使っていない

**コンテナが先、子が後。閉じるときは子が先、コンテナが後。** コンテナは中身が流れ込む前に開き、
中身はコンテナが閉じる前に出ていくべきだ。親子のオーケストレーション機構がないランタイムなら、
これはディレイ 2 つと算数 1 つでしかない。コンテナの退出は、子の退出が終わるまで始めない。

## 7. スクロール：連動は平滑化し、トリガーは一度だけ発火させる

**スクロールトリガー**（ビューポートに入ったら再生）

**一度だけ**発火させる。ほぼ常にこれが正しい——ユーザーが上下に行き来するたび再生される
アニメーションは酔うし、2 回目はどのみち何の情報も運んでいない。

**約 30% 見えた時点**で発火させる。最初の 1px ではない。1px の閾値では要素が画面のいちばん端に
いるうちに発火するので、ちゃんと視界に入る前にアニメーションが終わっている。

**スクロール連動**（スクロール位置に値を束縛する）

スクロール入力は離散的だ——ホイールの 1 ノッチ、トラックパッドのイベント、タッチのデルタ 1 フレーム分。
これを transform に直結すると、目に見えて段階的になる。**スプリングを通すのは気配りではなく必須だ。**
毎フレーム `target` をスクロール値にリセットするスプリングを走らせ、その出力でアニメーションさせる。

ここでは*柔らかい*スプリングを使う——`spring(0.35, 0)` あたり。これは動きではなくフィルタであり、
スクロール連動値でのオーバーシュートは、ページがユーザーに抵抗しているように読まれる。

必ず引っかかる細部が 2 つ：

- マウント時、スプリングは**現在のスクロール値で初期化**しなければならない。ゼロで初期化すると
  読み込み時にページが上から流れる。
- 固定はプラットフォームのネイティブな sticky／アンカー機構で行う。スクロールハンドラから毎フレーム
  位置を書き込んではいけない。

**パララックスの振幅**：背景レイヤーが前景の `0.3–0.5×` で動けば十分だ。それ以上は奥行きではなく
*背景が漂っている*と読まれ始める。

reduced motion で真っ先に無効化すべきものがパララックスだ。

## 8. ジェスチャーのフィードバックは 100ms 以内に始める

タッチとクリックのフィードバックは**確認のシグナル**であって、アニメーションではない。

```
hover:  scale 1.03      spring(0.15, 0)
press:  scale 0.97      spring(0.15, 0)
drag:   scale 1.03  +  wide shadow  +  raised depth order
```

- **押す＝小さくなる。** 指が押し下げているなら、そのものは沈むべきだ。大きくなるのは物理として誤り。
- ホバーのスケールは `1.05` を上限にする。それを超えると、隣の要素が押しのけられて見える。
- 大きな要素（カード、パネル）ではホバーのスケールを*小さく*する（`1.01–1.02`）。実際の変位は
  スケール × サイズなので、同じ比率でも大きな要素ではずっと遠くまで動く。
- ドラッグには必ず、つかんでいることが分かる専用の状態が要る。
- 境界は**弾性的に**表現する。限界を少し越えて引っ張らせ——距離に応じて抵抗を増やし、典型的には
  入力の半分だけ端を越えさせ——放したらスプリングで戻す。硬い壁はバグに読まれ、弾性的な抵抗は
  ルールに読まれる。
- 押下フィードバックの機構が何であれ、**キーボード操作**でも発火することを確かめる。クリックでは
  目に見えて沈むのに Enter では何も起きないボタンは、そもそも沈まないボタンより悪い。

## 9. 待機と不確実性

- **1 秒未満**：スピナーを出さない。ちらつくスピナーは、素直に待つより苛立たしい。
- **1–5 秒**：スケルトン。シマーはゆっくり（1 パス `1.5–2s`）、低コントラストで。*まだここにいる*と
  伝えるためのものであって、注意を奪い合ってはいけない。
- **5 秒超、または進捗が分かる場合**：プログレスバー。そして**決して逆戻りさせない**。
- 楽観的更新では、新しい項目を最終形（必要なら不透明度を落として）で挿入し、失敗したときだけ
  ロールバックをアニメーションさせる。**成功パスを見えなくすることが、最良のアニメーションだ。**

アンビエントなループ効果（呼吸、脈動、シマー）は、振幅を*気づくが読み取れない*程度に抑え、
周期は `≥ 1.5s`、そして reduced motion では常に無効にする。

## 10. アンチパターン

| アンチパターン | なぜ間違いか | 代わりに |
|---|---|---|
| 何にでも `dur 0.5` | 段階がない。すべてが等しく重要なら、何も重要ではない | `SKILL.md` §3.4 のタイミング段階 |
| `y: 100` / `scale: 0` からのフェードイン | 距離が大きすぎ、別の画面から来たように読まれる | `y 8–16px`、`scale 0.95` |
| スケールを弾ませる | ガラスにぶつかった感触 | `b = 0` |
| 移動に `linear` | 物理世界に等速で動き出し等速で止まるものはない | `out` かスプリング。`linear` はスクロール連動と無限回転だけ |
| 退出が出現と同じ長さ | すでに無関係なものを待たせる | 退出を 0.5–0.7× に切り詰める |
| 再生され直すスクロールトリガー | 酔うし、2 回目は情報を運ばない | 一度だけ発火させる |
| 算数をしない stagger | 最後の項目が 2 秒後に着地する | 間隔 × 個数 ≤ 0.5s |
| width / height / top / left のアニメーション | レイアウトを誘発し、フレームを落とす | transform、および §4 の計測して逆変換する手 |
| キャンセル不能なタイマーでの連鎖 | 割り込めず、ずれていく | まとめてキャンセルできるシーケンス |
| ライトテーマでしかテストしていない | 暗いサーフェスではシャドウが見えない | `contrast.md` を参照 |
| reduced motion 未対応 | 一部のユーザーにめまいを起こす | `SKILL.md` §5 |
| 同じ画面に `b = 0` と `b = 0.4` | インターフェースが寄せ集めに見える | プロダクト全体で 1 つのトークンセット |
| 「アニメーション完了」コールバックに本当のロジックを載せる | 割り込まれると発火しない | 状態は独立に駆動する。アニメーションは表現でしかない |

## 11. トークンを定義し、手作業のチューニングをやめる

自然に感じさせるもう半分は**一貫性**だ。プロダクト内で同じ意味を持つ操作は、同じタイミングと
カーブを共有すべきだ。これをランタイムの設定フォーマットで一度だけ書く：

```
feedback :  dur 0.12   curve out          # press, checkbox, focus ring
micro    :  dur 0.2    curve out          # hover, tooltip
enter    :  spring(0.3,  0.15)            # component entry
exit     :  dur 0.15   curve in           # component exit
layout   :  spring(0.35, 0)               # reflow
page     :  spring(0.5,  0.1)             # route change
stagger  :  0.04
lumin    :  dur 0.13   curve out          # brightness, colour, shadow tier
```

最後の行に注目。輝度が独自のトークンを持つのは、それが伴う動きよりも**速く**なければならない
からだ（`contrast.md` §5）。トークンセットに輝度の項目がないと、明度は結局その動きの持続時間を
共有することになり、*色がオブジェクトを追いかけている*ように読まれる。

そのうえで、逸脱が必要なときにだけ単一コンポーネントで上書きする——そして、理由を言えるときにだけ。
