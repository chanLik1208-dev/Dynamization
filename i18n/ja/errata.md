# errata.md — このパックが招く間違い

`pitfalls.md` は、目に見えて壊れていて症状を引くためのものだ。**このファイルは、どこも壊れて
見えないときのためのものだ。**

以下の項目はすべて、該当する章を読み、それに従っていた人が犯した間違いだ。そこが要点だ。これらは
知識の失敗ではなく、検証の失敗だ。どれも例外を投げない。どれも警告を出さない。そしてほとんどが
出荷される。

書く前に読み、完了だと言う前にもう一度読むこと。

---

## 使い方

各項目はまず**沈黙した症状**を挙げる。手に入るのはそれだけだからだ。次に誤ったコード、次に
有能な実装者がそれでもそう書いてしまう理由、次に対処、そして**実際に走らせられる確認 1 つ**。

要になるのは確認のほうだ。検証できない規則は、破ることになる規則だ。

## A. 章に従ったのに、環境がそれを食った

### A1. クリップする祖先が、あらかじめ描画したシャドウを打ち消す

**沈黙した症状：** ホバーで位置は変わるのに、エレベーションが一向に現れない。ライトテーマでは
`contrast.md` §2 が層のすべてをシャドウに預けているので、ホバーは動きだけを運ぶことになる——
まさに `SKILL.md` §5 が警告している半分だけの表現だ。

```css
/* ❌ */
.card { border-radius: 4px; overflow: hidden; box-shadow: var(--e2); }
.card::after { inset: 0; box-shadow: var(--e3); opacity: 0; transition: opacity .13s; }
.card:hover::after { opacity: 1; }
```

**なぜそう書かれるのか：** `contrast.md` §6 は `box-shadow` をアニメーションさせるのではなく、
あらかじめ描画したシャドウをクロスフェードしろと言っており、その助言は正しい。それとは別に、
上部に画像を持つ角丸カードは角をクリップする必要があり、カードへの `overflow: hidden` は反射的な
選択だ。どちらの判断も単独では正しい。シャドウは要素のボックスの*外側*に描かれるので、クリップは
それを消し去る——しかも黙って消す。トランジション自体は、誰にも見えないレイヤーの上で走り続ける
からだ。

```css
/* ✅ clip the thing that needs clipping, not the thing casting the shadow */
.card { border-radius: 4px; box-shadow: var(--e2); }          /* no overflow here */
.card .media { border-radius: 3px 3px 0 0; overflow: hidden; }
```

**確認方法：** その要素をホバーして、カードではなく*シャドウ*を見る。シャドウの変化が見えないなら、
祖先をさかのぼって `overflow: hidden`、`clip-path`、あるいは `CanvasGroup` 的なコンポジット用
ラッパーを探すこと。同じ罠は `outline-offset` で描いたフォーカスリングにも当てはまる。

---

### A2. 焼き込んだスプリングを `Dv` で再生すると速くなる

**沈黙した症状：** 動きの形は正しいのに急いで見え、オーバーシュートが収束ではなくパチンとした
動きになる。

```css
/* ❌ the curve is 0.32s long; the clock says 0.3s */
transition: translate .3s var(--spring-enter);
```

**なぜそう書かれるのか：** トークン表の他の行はすべて持続時間なので、`spring(0.3, 0.15)` も
「0.3 秒」と読める。違う。`Dv` は*視覚的*持続時間——動きが終わったように見える時点——であり、
焼き込んだカーブにはその後の収束の尾が必ず含まれる。この 2 つの数値は、スプリングが弾むほど
大きく食い違う。`b = 0.4` では尾が全体の 35% を占める。

```css
/* ✅ */
transition: translate .32s var(--spring-enter);   /* t_settle, from spring.md §4 */
```

**確認方法：** `spring.md` のトークン表では、どのスプリングにも `Dv` と `t_settle` の両方がある。
CSS の持続時間が `Dv` と一致しているなら、それは間違いだ。スタイルシートを `Dv` の値
——`.3s`、`.35s`、`.5s`——が `linear(` イージングの隣にある箇所で grep すること。

---

### A3. 進捗のクランプが、黙ってバウンスを消す

**沈黙した症状：** `b` を変えても何も変わらない。`spring(0.3, 0.15)` と `spring(0.3, 0.4)` が
同じに見えるので、バウンスは効果が微妙すぎると結論して使うのをやめてしまう。

**なぜそう書かれるのか：** サンプリング自体は正しくできているが、ランタイムが `0–1` の外側の
イージング値を拒否するかクランプしている。CSS の `linear()` は受け付けるが、enum ベースや
カーブアセットのシステムの多くは受け付けず、しかもエラーではなくクランプで処理する。

**対処：** 自分がどちらの環境にいるのかを一度調べ、アダプタに書いておく。進捗がクランプされるなら、
焼き込んだカーブで `b > 0` を実現することはできない——スプリングを積分する（`spring.md` §3）か、
`b = 0` を受け入れて、生き生きした感じは複数プロパティの規則から得ること。

**確認方法：** ピークが `1.094` になる `spring(0.3, 0.4)` を焼き込み、400px の translate に適用する。
要素が 400px を一度も越えないなら、進捗はクランプされている。

---

### A4. トランジションがホバー状態側に書かれていて、離れる動きが一瞬になる

**沈黙した症状：** ホバーに入るときは滑らかで、離れるときはスナップする。インタラクションの半分は
問題なく感じられ、残り半分がなぜ安っぽく感じるのか言葉にできない。

```css
/* ❌ */
.card:hover { translate: 0 -4px; transition: translate .2s; }
```

**なぜそう書かれるのか：** 自然に読めるからだ——「ホバーしたら 0.2s かけて上へ動く」——そして
テストしていた方向では実際に動く。この宣言はセレクタが一致しているあいだしか存在しないので、
ホバーが外れたときに走るトランジションが存在しない。

```css
/* ✅ the transition belongs to the resting state */
.card { transition: translate var(--t-micro); }
.card:hover { translate: 0 -4px; }
```

**確認方法：** ポインタを*離して*見る。どの状態も、出現ではなく退出を必ずテストすること——これは
`feel.md` §5 を自分のテストに適用したもので、A4、A5、C1 を一度に捕まえる。

---

### A5. 直前の値が存在しないので、何も入ってこない

**沈黙した症状：** 要素がただ出現する。エラーも、途中まで再生されたアニメーションもない。

**なぜそう書かれるのか：** トランジションは 2 つの計算済み値のあいだを補間するが、挿入されたばかりの
要素——あるいは `display: none` だった要素——には、出発する最初の値が存在しない。宣言に問題は
ない。やることが何もないだけだ。

**対処：** CSS なら `@starting-style` と `transition-behavior: allow-discrete`（`adapters/css.md`）。
スクリプトなら、開始値を設定し、リフローを強制してから終了値を設定する——何もしていないように
見えて実はしている、あの `void el.offsetWidth` の行だ。そうした機構のないランタイムなら、開始値で
マウントし、次のフレームで変更する。

**確認方法：** 出現アニメーションが 1 フレーム前に存在しなかった要素を含むなら、この 3 つのどれかが
必要だ。4 つ目の選択肢はない。

## B. このパックが明示している規則を破った

### B1. レイアウトプロパティでものを動かす

**沈黙した症状：** 見た目は正しい動きなのに、中位機種のスマートフォンではフレームを落とし、
自分のマシンでは問題ない。

```js
/* ❌ — and this was written by someone implementing this very pack */
flier.style.transition = "left .32s var(--spring), top .32s var(--spring), width .32s, height .32s";
flier.style.left = to.left + "px";
```

**なぜそう書かれるのか：** `getBoundingClientRect()` から 2 つの矩形が手に入り、それらは
`left`/`top`/`width`/`height` で表現されている。すでに手元にある数値をアニメーションさせるのが
計測から動きへの最短経路であり、結果の形も正しいので、見直す動機が何も生まれない。

```js
/* ✅ place it at the destination, move it with a transform */
flier.style.left = to.left + "px";
flier.style.top = to.top + "px";
flier.style.width = to.width + "px";
flier.style.height = to.height + "px";
flier.style.translate = (from.left - to.left) + "px " + (from.top - to.top) + "px";
flier.style.scale = from.width / to.width;
/* next frame: animate both back to identity */
```

**確認方法：** 自分が書いたアニメーションを `left`、`top`、`width`、`height`、`margin`、`padding`
で grep する。ヒットするたびに理由が要る。`feel.md` §4 の計測して逆変換する手順は、答えが常に
transform になるように存在している。

---

### B2. 1 つのイベント、1 つのプロパティ

**沈黙した症状：** インタラクションは反応するのに、それが何を意味するのか誰も説明できない。
それ以上の詳細のない「安っぽく感じる」が典型的な報告だ。

**なぜそう書かれるのか：** 各プロパティが別々のタイミングで足されるからだ。動きはコンポーネントを
作るときに入り、シャドウはデザインレビューの指摘で入り、サーフェスの変化はリファクタで消える。
どのコミット単体を見ても間違って見えない。

**対処：** `SKILL.md` §3.5 の各行を、メニューではなく最低ラインとして扱うこと。持ち上げは変位
**かつ**より大きく柔らかいシャドウ**かつ**明るいサーフェスだ。押下はスケール縮小**かつ**締まった
シャドウ**かつ**暗くなること。

**確認方法：** インタラクションごとに変化しているプロパティの数を数える。持ち上げや押下で 3 つ未満
なら未完成だ——そして 3 つのうち 1 つがシャドウなら、A1 の確認をもう一度走らせること。シャドウが
黙って消えるのはそこだ。

### B3. 対称な退出

**沈黙した症状：** インターフェース全体がわずかに鈍く感じられるのに、指させるほど遅い箇所が
1 つもない。

**なぜそう書かれるのか：** 退出はたいてい出現の鏡像として書かれる。編集が 2 回ではなく 1 回で
済むからだ。そしてそれは*間違い*ではない——ただ 40% 長すぎ、必要な距離の 2 倍以上を走るだけだ。

**対処：** 退出は出現の `0.5–0.7×` の長さ、距離は半分以下、カーブは `in`。

**確認方法：** トークンセットの中の退出の持続時間をすべて見つけ、対応する出現と比べる。2 分で
終わる監査であり、プロダクト全体の感触が変わる。

---

### B4. 2 つのスプリング語彙を混ぜる

**沈黙した症状：** パラメータのどれかが効かない。`bounce` を変えても違いが見えないので、値が
小さすぎるのだと思い込み、何かが動くまで押し上げてしまう。

```js
/* ❌ */
{ type: "spring", visualDuration: 0.3, bounce: 0.2, stiffness: 400 }
```

**なぜそう書かれるのか：** `stiffness` で書かれたスプリングを引き継ぎ、感触を調整したくなって、
自分が理解しているパラメータに手を伸ばした——古いほうを残したまま。ほとんどの実装は、片方の
体系を黙って無視することでこれを解決する。

**対処：** プロジェクトごとに語彙は 1 つ。`Dv`/`b` を優先し、`spring.md` §2 で境界において変換する。

**確認方法：** `stiffness` と `damping` で grep する。ヒットはすべて変換関数の内側にあるべきで、
それ以外の場所にはあってはならない。

## C. アニメーションにロジックをぶら下げた

### C1. 完了イベントでノードを削除する

**沈黙した症状：** 見えない要素がツリーに溜まり、クリックを横取りする。素早く操作するユーザーに
しか起きないので、見ているあいだは再現しない。

```js
/* ❌ */
el.addEventListener("transitionend", () => el.remove());
```

**なぜそう書かれるのか：** まさにこの用途のために文書化されたイベントであり、テストするたびに動く
——なぜなら 1 回クリックして待つというやり方でテストするからだ。

```js
/* ✅ the animation is presentation; the removal is not */
el.classList.add("leaving");
setTimeout(() => el.remove(), EXIT_MS);
```

**理由：** 完了イベントは、アニメーションがキャンセルされたとき、割り込まれたとき、置き換えられた
とき、reduced motion でスキップされたときには発火しない——そして Promise ベースの API はそうした
場合に*reject* するので、キャッチしていない `await` はノードを永久に残す。4 つとも普通の状況で
あって、エッジケースではない。

**確認方法：** 退出をトリガーし、すぐにもう一度トリガーするか、飛行中に反転させる。それから
ツリーを調べる。あわせて、reduced motion をオンにして、それでもものが削除されることを確認する。

---

### C2. アニメーションが真実の源になっている

**沈黙した症状：** 割り込まれたトランジションの後、開いても閉じてもいないメニューが残り、その後の
トグルが逆の動作をする。

**なぜそう書かれるのか：** 視覚的な状態と論理的な状態は同じ事実に見えるので、変数を 1 つに保つのが
良い衛生に思える。

**対処：** boolean を持つこと。それに向かってアニメーションさせること。`pitfalls.md` §7 のテストは
正確だ：**プロダクトからアニメーションをすべて削除しても、ロジックはすべて動くはずだ。**

**確認方法：** すべての持続時間を `0.01ms` にしてプロダクトを使う。すべて動くはずだ。次に `2s` に
して、いろいろ割り込む。答えは同じであるべきだ。

## D. 検証していないものを信じた

### D1. 記憶から書いた API 名

**沈黙した症状：** ガードされた読み取りでは何も起きない——ガードが飲み込み、その機能は永久に
オフになる。ガードのない読み取りでは、誰も通らないコードパスでクラッシュする。

```lua
-- ❌ the guard makes a wrong name indistinguishable from an absent one
local ok = pcall(function() reduced = GuiService.ReducedMotion end)
```

**なぜそう書かれるのか：** 名前は*ほぼ*合っており、防御的なコードは良い習慣だ。この 2 つが揃うと、
黙って存在しない機能ができあがる——対処済みに見えるぶん、ありうる中で最悪の結果だ。

**確認方法：** 出荷する前に、名前は自分の記憶からではなくプラットフォーム自身の API 一覧から
読み取ること。ガードは*古いクライアントに存在しないかもしれない*プロパティのためのものであり、
名前を知っていることの代わりにはならない。ガードされた読み取りが失敗したら、黙って既定値に
落とすのではなく、開発時にログを出すこと。

---

### D2. ドキュメントが約束していない保証を主張する

**沈黙した症状：** 誰かがその主張の上に何かを作るまで、何も起きない。そして、どのコード行でもなく
文書の一文にたどり着くバグが出る。

**なぜそう書かれるのか：** あるケースを明らかに*扱うべき*コンポーネントはたいてい実際に扱うし、
「X を扱う」と書くほうが「X は自分で検証すること」と書くより短い。

**対処：** ドキュメントが述べていることを述べる。正しいと信じているが出典を示せないものは、その
とおりの言葉で書き、確認方法を書き添えること。

**確認方法：** 自分が書いたものの中の能力に関する主張ひとつひとつについて、どこで読んだのかを問う。
「理屈からしてそうだ」は出典ではない。

---

### D3. 手で作った数値

**沈黙した症状：** *おおよそ*正しいカーブ。アニメーションはするし、スプリングに見えるし、読んだ
だけではどのレビュアーも捕まえられない形で間違っている。

**なぜそう書かれるのか：** 21 個の値からなるイージング表は、形から推定できそうな種類のものに見え、
その結果はざっと見るぶんには十分もっともらしい。

**対処：** 計算すること。`spring.md` §4 に減衰域ごとの閉形式がある。10 行のスクリプトで表が
できる。そのうえで端点とピークを、公開されている数値と突き合わせること。

**確認方法：** 2 つの不変条件でほぼすべてを捕まえられる——表はちょうど `0` で始まり、ちょうど `1` で
終わらなければならない。そしてピークは `spring.md` §1 のその `b` に対応するオーバーシュートと
一致しなければならない。戻りで 1 を*下回る*ことのない「弾む」カーブはスプリングではない。手で
描いた弧だ。

## E. 文書そのものにおける規律

### E1. ランタイム非依存のファイルに紛れ込んだライブラリの識別子

**沈黙した症状：** 意味の通らない一文と、自分のランタイムに存在しない API を探しに行かされる読者。

> ❌ Items inside: `stagger 0.03`, starting after the container is `beforeChildren`.

**なぜそう書かれるのか：** その規則はある実装から学ばれたもので、その実装が付けた名前は規則そのもの
より短い。周囲の文章が中立に書き直されても、識別子は専門用語のように見えるので生き残ってしまう。

> ✅ Items inside: `stagger 0.03`, beginning only once the container has finished opening — the
> container-before-children rule in `feel.md` §6.

**確認方法：** 判断を扱う章を、特定ライブラリの語彙で grep する。API を名指ししないと冒頭で
約束しているファイルは、それを証明できるべきだ。

---

### E2. 誤った節への相互参照

**沈黙した症状：** 読者がポインタをたどり、無関係な内容にたどり着き、他の参照も静かに信じなくなる。

**確認方法：** 自分が書いた `§N` ひとつひとつについて、その §N を開く。機械的で退屈だが、この
ファイルの中でいちばん命中率の高い確認だ——相互参照は文書を再編するたびに腐り、ツールチェーンの
何もそれに気づかない。
