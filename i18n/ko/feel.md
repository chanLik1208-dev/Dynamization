# feel.md — 모션이 진짜처럼 읽히게 만드는 것

이 파일은 API에 관한 것이 아니다. *왜 그 애니메이션이 가짜처럼 보이는지*에 관한 것이다.

각 문제가 환영을 얼마나 심하게 깨뜨리는지 순서로 대략 정렬해 두었다. **앞의 것부터 고쳐라. 뒤의 세부 사항은
앞이 맞아떨어진 다음에야 의미가 있다.**

여기 있는 모든 것은 `SKILL.md` §1의 스펙 어휘로 쓰여 있다. 플랫폼에 종속된 내용은 하나도 없다.

---

## 0. 한 줄 원칙

> 애니메이션은 사람들이 **생각하지 않고도** 무슨 일이 일어났는지 알게 해야 한다.
> 사용자가 애니메이션을 알아채면 안 된다. *저것이 저기서 왔다*는 것을 알아채야 한다.

사람들이 멈춰 서서 *감상하는* 애니메이션은, 제품 안에서는 거의 언제나 너무 길다.

---

## 1. 파라미터는 애니메이션되는 값이 고르게 하라

무엇을 써야 할지 확신이 없을 때 **뭔가를 지어내지 마라.** *어떤 종류의 값이 움직이는지*로 고르면 선택은 이미
끝나 있다.

| 무엇이 움직이는가 | 무엇을 쓰는가 |
|---|---|
| 키프레임 세 개 이상 | 트윈, `dur 0.8`, curve `inout` |
| 위치와 회전 — `x` `y` `z` `rotate` `skew` | `spring(0.28, 0.2)` — 약간의 오버슈트 |
| scale 계열 | `spring(0.27, 0)` — **오버슈트 없음** |
| 그 밖의 전부 — 불투명도, 색, 블러, 필터 | 트윈, `dur 0.3`, curve `out` |

마지막 행의 곡선은 정확히 이름 붙여 둘 값어치가 있다. 플랫폼 기본값보다 **더 완만한 easeOut**이다. 시작이
덜 급하고, 끝은 똑같이 부드럽다. 3차 베지에로는 `(0.25, 0.1, 0.35, 1)`, 이름 붙은 곡선을 쓰는 런타임에서는
"quint out"이 아니라 "sine out"이나 "quad out"이다.

**저 표에서 곧바로 읽어낼 수 있는 결론 세 가지:**

1. 공간을 차지하는 것(위치, 크기) → spring. 차지하지 않는 것(불투명도, 색) → 트윈.
2. 커지고 작아지는 것은 **바운스하면 안 된다.** 움직이는 것은 해도 된다.
3. 기본 지속 시간은 고작 `0.3s`다. 그보다 길다면 이유가 필요하다.

## 2. spring의 진짜 가치는 통통 튀는 맛이 아니라 속도 인계다

대부분은 spring = 튕김이라고 생각한다. 틀렸다. 가장 중요한 성질은 **애니메이션이 인터럽트됐을 때 현재
위치에서 현재 속도로 이어진다는 것**이다. 딱 멈춰 서서 처음부터 다시 시작하는 게 아니라.

*물체처럼 느껴지는 것*과 *슬라이드쇼처럼 느껴지는 것*을 가르는 선이 여기다.

어느 쪽 애니메이션도 끝나기 전에 두 목표 사이를 왔다 갔다 토글하는 값을 생각해 보자.

- **트윈**은 토글할 때마다 강제로 재시작한다. 매 재시작은 속도 0에서 시작하므로, 사용자가 행동한 바로 그 순간
  — 그들이 보고 있는 정확히 그 순간에 — 움직임이 눈에 띄게 덜컥거린다.
- 목표가 옮겨진 **spring**은 위치와 속도를 유지한다. 방향을 되돌리면 관성 있는 무언가를 밀치는 느낌이 나는데,
  적분이 문자 그대로 그 일을 하고 있기 때문이다.

**판별법: 이 애니메이션은 사용자의 직접 행동으로 트리거되는가?**

| 트리거 | 무엇을 쓰는가 | 이유 |
|---|---|---|
| 드래그, 스와이프, 제스처, 커서 따라가기 | **spring** (필수) | 이어받을 실제 속도가 있다 |
| 클릭 / 호버로 생기는 이동이나 크기 변화 | **spring** | 반복해서 인터럽트될 수 있다 |
| 토글로 생기는 레이아웃 변경 | **spring** | 위와 같다 |
| 등장 / 퇴장 페이드 | **트윈** | 이어받을 속도가 없고, 타이밍 제어가 더 중요하다 |
| 시간을 맞춰야 하는 것(stagger, 시퀀스, 영상) | **트윈** | spring에는 믿을 만한 종료 시각이 없다 |
| 스크롤 연동 | 직접 바인딩한 뒤 스무딩 | §7 참조 |

**Tier 2** 런타임(`SKILL.md` §2)에서도 인터럽트는 되지만 속도는 잃는다. 완화책은 두 가지, 선호 순서대로다.
실제로 제스처 기반인 몇 안 되는 인터랙션에 대해서만 spring을 직접 적분하고(`spring.md` §3 — 열다섯 줄이다),
나머지 전부에서는 인터럽트 시점의 **현재** 값을 읽어 거기서부터 `b ≤ 0.15`로 애니메이션하라. 그러면 재시작이
덜컥거림으로 읽히지 않을 만큼 작게 유지된다.

**Tier 3**에서는 맞서 싸우지 마라. 재트리거 가능한 애니메이션은 `dur ≤ 0.2s`로 유지하라. 그 아래에서는 강제
재시작이 지각 하한 밑이라 아무도 보지 못한다.

## 3. 원시 계수가 아니라 `Dv` + `b`로 조율하라

`stiffness: 400, damping: 32`를 머릿속에 그릴 수 있는 사람은 없고, 두 손잡이는 서로 간섭한다. 그래서
"조금만 더 빠르게"가 재설계로 번진다. 시각적 지속 시간과 바운스로 작업하고, 경계에서 한 번만 변환하라.

전체 변환식, 각 바운스 값이 실제로 만드는 오버슈트, 그리고 적분기 →
`references/spring.md`.

짧은 버전:

- `b`는 *얼마나 지나쳐 가는가*다. `0.15`는 목표를 약 0.6% 지나가고, `0.4`는 약 9.5% 지나간다.
- `Dv`는 *보기에 얼마나 걸리는가*다. 꼬리는 그 뒤에 일어나고, 그 덕분에 spring과 트윈을 나란히 놓고 비교할 수
  있다.
- scale은 언제나 `b = 0`이다.
- 제품당 `b` 하나. 바운스가 뒤섞여 있는 것은 서로 말을 섞은 적 없는 여러 사람이 만든 인터페이스임을 가장
  분명하게 드러내는 신호다.

## 4. 인과: 물건은 그것이 온 곳에서 온다

이걸 어기면 곡선을 아무리 다듬어도 살아나지 않는다.

- 드롭다운은 **그것을 연 컨트롤에서** 펼쳐진다. 화면 한가운데서 페이드인하지 않는다. transform origin(또는
  앵커 포인트)을 컨트롤 위에 놓아라.
- 모달은 클릭된 카드에서 자라난다. 런타임이 한 요소를 다른 요소의 위치로 애니메이션할 수 있다면 그렇게 하고,
  못한다면 최소한 모달을 카드의 위치와 크기에서 시작해 움직여라. 페이드 말고.
- 사이드바는 **자기 쪽 가장자리에서** 밀려 들어온다. 아래에서가 아니라.
- 목록 항목을 지우면 나머지가 **그것이 남긴 틈을 메운다.** 뛰어넘는 게 아니라.
- 토스트는 자기가 자리 잡을 모서리에서 들어온다.

**내장 기능이 없는 런타임에서 공유 요소를 다루는 일반 절차:**

```
1. 변경 전에 출발 rect를 측정한다        (위치, 크기)
2. 레이아웃 변경을 즉시 일어나게 둔다
3. 도착 rect를 측정한다
4. 역변환을 적용해 시각적으로 출발 위치에 되돌려 놓는다
5. 그 transform을 항등으로 애니메이션한다
```

transform만 움직이므로, 레이아웃 애니메이션처럼 보여도 컴포지터 관점에서는 싸다. 사각형을 측정하고 transform을
적용할 수 있는 런타임이면 어디서든 동작하는데, 그건 곧 전부다.

**travel 거리의 감각:** 마이크로 인터랙션 `4–12px`, 컴포넌트 전환 `16–40px`, 백분율은 전체 화면 이동에만.

`y: 100`에서 페이드인하는 것은 가장 흔한 실수다. 툴팁이라면 그 거리는 *다른 방에서 도착하는* 것으로 읽힌다.

## 5. 비대칭적인 등장과 퇴장

| | 등장 | 퇴장 |
|---|---|---|
| 지속 시간 | `0.2 – 0.35s` | 등장의 **0.5 – 0.7×** |
| Curve | `out` / spring | `in` |
| 거리 | 전체 | **절반 이하** |
| 시작 scale | `0.95` (`0`이 아니다) | `0.98` (거의 줄지 않는다) |

이유: 등장할 때 사용자는 새 정보를 *붙잡아야* 하고 그것을 찾아낼 시간이 필요하다. 퇴장할 때 그것은 이미 사용자와
무관하며, 기다리게 하는 것은 그들의 시간을 낭비하는 일이다.

들어올 때 `out`, 나갈 때 `in`은 경험 전체에 걸쳐 하나의 `inout`으로 합성된다.

`scale: 0`에서 등장시키지 마라. 그것은 *무에서 존재로*라는 뜻인데, UI 요소는 거의 언제나 *어딘가 다른 곳에서*
온다. "이게 나타났다"고 말하기엔 `0.95`면 충분하고도 남는다.

**메커니즘이 필요한 쪽은 퇴장이다.** 등장 애니메이션은 쉽다. 그것이 존재하니 애니메이션하면 된다. 퇴장은 논리적으로
이미 제거된 무언가를 살려 두어야 한다. 런타임마다 이 문제를 다르게 푸는데, 이것이 "퇴장 애니메이션이 아예 안
나온다"의 1번 원인이다. 퇴장을 설계하기 *전에* 어댑터에서 그 메커니즘을 찾아라. 설계한 뒤가 아니라.

## 6. 오케스트레이션: stagger는 리듬이지 장식이 아니다

열 개가 동시에 나타나면 하나의 덩어리로 읽힌다. 어긋나게 놓으면 순서가, 그리고 방향이 생긴다.

**간격 고르기:**

| 항목 수 | 간격 | 총 예산 |
|---|---|---|
| 3–6 (메뉴, 카드 한 줄) | `0.04 – 0.06s` | ≤ 0.35s |
| 7–15 (목록) | `0.02 – 0.04s` | ≤ 0.5s |
| 글자 단위 | `0.02 – 0.03s` | 길이에 따라 다름. 1s를 넘으면 단어 단위로 바꿔라 |
| 20개 초과 | 개별 stagger 금지 | 묶어서 처리하거나 전체를 페이드해라 |

**총합은 절대 상한이다.** 20개 항목에 `0.1s` stagger면 2초다. 마지막 항목이 도착할 즈음 사용자는 다른 일을
하고 있다. 쓰기 전에 산수를 해라.

**방향에는 의미가 있어야 한다:**
- **처음부터** — 위에서 아래로, 읽는 순서와 일치, 안전한 선택
- **마지막부터** — 접을 때. 위로 되말려 올라가 보인다
- **가운데부터** — 바깥으로 열림, 의례적, 히어로에 좋다
- **사용자가 방금 건드린 항목부터** — 바깥으로 퍼져 나감 ← **가능한 가장 강한 인과 진술**이고, 거의 아무도
  쓰지 않는다

**컨테이너 먼저 자식 나중, 자식 먼저 컨테이너 나중.** 컨테이너가 먼저 열린 뒤 내용이 쏟아져 들어와야 하고,
내용이 빠져나간 뒤 컨테이너가 닫혀야 한다. 런타임에 부모/자식 오케스트레이션이 없다면 이건 지연 두 개와 산수
한 번일 뿐이다. 컨테이너의 퇴장은 자식들의 퇴장이 끝나기 전에 시작되면 안 된다.

## 7. 스크롤: 연동은 스무딩해야 하고, 트리거는 한 번만 발화해야 한다

**스크롤 트리거**(뷰포트에 들어올 때 재생)

**한 번만** 발화하라. 이게 거의 언제나 맞다. 사용자가 위아래로 스크롤할 때마다 다시 재생되는 애니메이션은
멀미를 유발하고, 두 번째 재생은 어차피 아무 정보도 담고 있지 않다.

첫 픽셀이 아니라 약 **30% 보일 때** 발화하라. 1픽셀 임계값은 요소가 아직 화면 맨 끝에 있을 때 발화하므로,
제대로 보이기도 전에 애니메이션이 끝나 있다.

**스크롤 연동**(스크롤 위치에 값을 묶음)

스크롤 입력은 이산적이다. 휠 노치 하나, 트랙패드 이벤트 하나, 터치 델타 한 프레임. 이걸 곧장 transform에
묶으면 눈에 보이는 계단 현상이 생긴다. **spring을 통과시키는 것은 필수이지 사치가 아니다.** 매 프레임
`target`을 스크롤 값으로 재설정하는 spring을 돌리고, 그 spring의 출력으로 애니메이션하라.

여기서는 *부드러운* spring을 써라. `spring(0.35, 0)` 정도. 이건 움직임이 아니라 필터다. 스크롤 연동 값에서
오버슈트는 페이지가 사용자와 싸우는 것으로 읽힌다.

늘 발목을 잡는 두 가지 세부 사항:

- 마운트할 때 spring은 0이 아니라 **현재 스크롤 값으로 초기화**해야 한다. 아니면 로드할 때 페이지가 맨 위에서
  훑고 내려온다.
- 고정은 플랫폼의 네이티브 sticky/앵커 메커니즘으로 하라. 스크롤 핸들러에서 매 프레임 위치를 써넣는 방식은 절대
  안 된다.

**패럴랙스 진폭:** 배경 레이어가 전경의 `0.3–0.5×`로 움직이면 충분하다. 그 이상이면 깊이로 읽히기를 멈추고
*배경이 떠내려간다*로 읽히기 시작한다.

패럴랙스는 reduced motion에서 가장 먼저 꺼야 할 대상이다.

## 8. 제스처 피드백은 100ms 안에 시작해야 한다

터치와 클릭 피드백은 애니메이션이 아니라 **확인 신호**다.

```
hover:  scale 1.03      spring(0.15, 0)
press:  scale 0.97      spring(0.15, 0)
drag:   scale 1.03  +  wide shadow  +  raised depth order
```

- **프레스는 작아지는 것이다.** 손가락이 눌러 내리면 그것은 눌려 들어가야 한다. 커지는 것은 틀린 물리다.
- 호버 scale은 `1.05`에서 잘라라. 그 이상이면 이웃 요소들이 밀려난 것처럼 보인다.
- 큰 요소(카드, 패널)는 호버 scale을 *더 작게* 잡아야 한다(`1.01–1.02`). 실제 변위 = scale × 크기이므로,
  같은 비율이라도 큰 요소에서는 훨씬 멀리 움직이기 때문이다.
- 드래그에는 언제나 구별되는 붙잡힘 상태가 필요하다. 사용자가 그것을 쥐고 있음을 알아야 한다.
- 경계는 **탄성적으로** 표현하라. 한계를 조금 넘어서 끌 수 있게 하고 — 거리에 따라 저항이 커지며, 보통 입력의
  절반만큼 넘어가게 — 놓으면 스프링백시켜라. 딱딱한 벽은 버그로 읽히고, 탄성 저항은 규칙으로 읽힌다.
- 프레스 피드백 메커니즘이 무엇이든 **키보드 활성화**에서도 발화하는지 확인하라. 클릭하면 눈에 띄게 눌리는데
  Enter에는 아무 반응이 없는 버튼은, 아예 눌리지 않는 버튼보다 나쁘다.

---

## 9. 기다림과 불확실성

- **1초 미만**: 스피너 없음. 번쩍하고 사라지는 스피너는 그냥 기다리는 것보다 더 짜증난다.
- **1–5초**: 스켈레톤. 그 셔머는 느리고(한 번 지나가는 데 `1.5–2s`) 저대비여야 한다. *아직 여기 있다*는
  신호일 뿐, 주의를 놓고 경쟁해서는 안 된다.
- **5초 초과, 또는 진행률을 알 수 있을 때**: 진행 표시줄. 그리고 그것은 **절대 뒤로 가지 않는다.**
- 낙관적 업데이트에서는 새 항목을 최종 형태로 삽입하고(원한다면 불투명도를 낮춰서), 실패했을 때만 롤백을
  애니메이션하라. **성공 경로를 보이지 않게 만드는 것이 최고의 애니메이션이다.**

주변에서 반복되는 앰비언트 효과(숨쉬기, 맥동, 셔머): 진폭은 *알아챌 수는 있으나 읽히지는 않을* 만큼 작게,
주기는 `≥ 1.5s`, 그리고 reduced motion에서는 언제나 꺼라.

## 10. 안티패턴

| 안티패턴 | 왜 틀렸는가 | 대신 |
|---|---|---|
| 전부 `dur 0.5` | 계층이 없다. 전부 똑같이 중요하면 아무것도 중요하지 않다 | `SKILL.md` §3.4의 타이밍 tier |
| `y: 100` / `scale: 0`에서 페이드인 | 거리가 너무 크다. 다른 화면에서 도착하는 것으로 읽힌다 | `y 8–16px`, `scale 0.95` |
| scale을 바운스시키기 | 유리에 부딪히는 느낌 | `b = 0` |
| 움직임에 `linear` | 물리 세계의 그 무엇도 등속으로 출발하고 정지하지 않는다 | `out` 또는 spring. `linear`는 스크롤 연동과 무한 회전 전용이다 |
| 퇴장을 등장만큼 길게 | 이미 무관해진 것을 기다리게 만든다 | 퇴장을 0.5–0.7×로 줄여라 |
| 다시 재생되는 스크롤 트리거 애니메이션 | 멀미가 나고, 두 번째에는 아무 정보도 없다 | 한 번만 발화 |
| 산수 없이 stagger 쓰기 | 마지막 항목이 2초 뒤에 도착한다 | 간격 × 개수 ≤ 0.5s |
| width / height / top / left 애니메이션 | 레이아웃을 유발하고 프레임을 떨어뜨린다 | transform, 그리고 §4의 측정-역변환 수법 |
| 취소 불가능한 타이머로 이어 붙이기 | 인터럽트할 수 없고 어긋난다 | 하나의 단위로 취소 가능한 시퀀스 |
| 라이트 테마에서만 테스트 | 어두운 서피스에서는 그림자가 보이지 않는다 | `contrast.md` 참조 |
| reduced motion 처리 없음 | 일부 사용자에게 어지럼증을 유발한다 | `SKILL.md` §5 |
| 같은 페이지에 `b = 0`과 `b = 0.4` | 인터페이스가 부품을 짜맞춘 것처럼 보인다 | 제품 전체에 토큰 세트 하나 |
| 실제 로직을 "애니메이션 완료" 콜백에 매달기 | 인터럽트되면 절대 발화하지 않는다 | 상태는 독립적으로 구동하라. 애니메이션은 표현이다 |

## 11. 토큰을 정의하고, 손으로 조율하는 것을 그만둬라

자연스럽게 느껴지는 것의 나머지 절반은 **일관성**이다. 한 제품 안에서 같은 의미의 행동은 같은 타이밍과 곡선을
공유해야 한다. 런타임의 설정 포맷이 무엇이든, 이걸 한 번 써 둬라.

```
feedback :  dur 0.12   curve out          # press, checkbox, focus ring
micro    :  dur 0.2    curve out          # hover, tooltip
enter    :  spring(0.3,  0.15)            # component entry
exit     :  dur 0.15   curve in           # component exit
layout   :  spring(0.35, 0)               # reflow
page     :  spring(0.5,  0.1)             # route change
stagger  :  0.04
lumin    :  dur 0.13   curve out          # brightness, colour, shadow tier
```

마지막 행을 눈여겨봐라. 휘도가 자기 토큰을 갖는 이유는 그것이 동반하는 움직임보다 **빨라야** 하기
때문이다(`contrast.md` §5). 토큰 세트에 휘도 항목이 없으면 밝기는 결국 움직임의 지속 시간을 같이 쓰게 되고,
*색이 물체를 뒤쫓는* 것으로 읽힌다.

그다음부터는, 벗어나야 할 때만 개별 컴포넌트에서 오버라이드하라. 그리고 그 이유를 말할 수 있을 때만.
