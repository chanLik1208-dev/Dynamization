# pitfalls.md — 증상 → 원인 → 해결

증상을 찾은 뒤 해당 절을 읽어라. 원인은 API가 아니라 *메커니즘*으로 묶여 있어서 런타임 사이를 그대로 넘어간다.
사라진 퇴장 애니메이션은 웹 프레임워크에서든 게임 엔진에서든 네이티브 툴킷에서든 똑같은 세 가지 원인을 갖는다.

| 증상 | 가장 유력한 원인 |
|---|---|
| 퇴장 애니메이션이 아예 안 나온다 | 애니메이션할 새도 없이 대상이 파괴됐다 → §1 |
| 트리거할 때마다 애니메이션이 처음부터 다시 시작한다 | 애니메이션 대상 객체가 매번 새로 만들어지고 있거나, 명목상의 시작값에서 재타깃하고 있다 → §2 |
| 역방향 전환이 버벅이거나 급정거한다 | 속도가 이어지지 않는다. Tier 2 동작이다 → §2 |
| 리플로우 애니메이션이 아무것도 안 한다 | 레이아웃이 바뀌었다고 시스템에 알린 게 없거나, 그 요소 타입이 transform될 수 없다 → §3 |
| 콘텐츠가 늘어나거나 모서리 반경이 타원이 된다 | rect를 scale하면서 내용물을 역스케일하지 않았다 → §3 |
| 스크롤하는 동안 페이지 전체가 떨린다 | 스크롤바나 안전 영역이 나타나면서 리플로우 애니메이션을 유발하고 있다 → §3 |
| 프레임이 떨어진다, 버벅인다 | 레이아웃 계층이나 페인트 계층 속성을 애니메이션하고 있다 → §4 |
| 스크롤 연동 값이 눈에 띄게 계단처럼 움직인다 | 스크롤 입력을 스무딩하지 않고 날것으로 썼다 → §5 |
| 로드할 때 화면이 맨 위에서 훑고 내려온다 | 스크롤 구동 spring을 0으로 초기화했다 → §5 |
| 드래그 거리가 포인터와 안 맞는다 | transform이나 scale이 걸린 조상 요소가 좌표계를 바꿨다 → §6 |
| 터치 기기에서 호버가 "박힌다" | 합성된 호버 이벤트 → §6 |
| 애니메이션은 끝났는데 상태가 안 바뀌었다 | 끝내 발화하지 않은 완료 콜백에 로직을 매달았다 → §7 |
| 다크 테마에서 엘리베이션이 사라진다 | 어두운 서피스에서는 그림자가 보이지 않는다 → `contrast.md` §2 |
| 애니메이션 도중 텍스트를 읽을 수 없다 | 중간 대비가 너무 낮다 → `contrast.md` §7 |

## 1. 일어나지 않는 퇴장

퇴장 애니메이션은 모순이다. 논리적으로 더 이상 존재하지 않는 것을 애니메이션하고 있으니까. 모든 런타임은 그
시간 동안 그것을 살려 둘 메커니즘이 필요하고, **실패는 언제나 셋 중 하나다.**

1. **살려 두는 장치가 제거되는 대상 안에 있다.** 파괴를 미루는 역할을 맡은 래퍼 자체가 같은 조건으로 파괴되면,
   애니메이션할 것이 아무것도 남지 않는다. 살려 두는 장치는 조건문 **바깥**에 있어야 하고, 조건은 그 안에 있어야
   한다.
2. **아이덴티티가 불안정하다.** 시스템은 어떤 키로 "어느 항목이 어느 것인지"를 추적한다. 그 키가 위치 인덱스라면
   항목 2를 지웠을 때 항목 3이 항목 2가 *되고*, 시스템은 제거가 아니라 갱신으로 본다. 안정적이고 고유한 id를
   써라.
3. **떠나는 것이 살려 두는 장치의 직계 자식이 아니다.** 중간에 아무 일도 안 하는 래퍼 하나만 끼어도 메커니즘이
   그것을 보지 못한다. 소스 트리가 아니라 실제 트리를 확인하라.

**중첩된 퇴장**은 그 자체로 함정이다. 서브트리 전체가 한꺼번에 제거되면 자식들은 대개 자기 퇴장을 재생하지
**못한다.** 부모가 먼저 끝나면서 자식들을 데려가 버린다. 자식이 먼저 떠나야 한다면 순서를 명시적으로
잡아라(`feel.md` §6: 내용이 빠져나간 *다음에* 컨테이너가 닫힌다).

**설계 판별법:** 퇴장하는 동안 요소를 살려 두는 메커니즘의 이름을 댈 수 없다면, 아직 퇴장 애니메이션을 가진 게
아니다. 설계하기 전에 어댑터에서 그것을 찾아라.

## 2. 재시작, 재생성, 그리고 잃어버린 속도

**애니메이션 대상 객체가 매번 새로 만들어지고 있다.** 렌더/업데이트 함수 안에서 생성되는 것은 매 프레임 또는 매
업데이트마다 새 객체이고, 이전 객체의 애니메이션 상태를 하나도 물려받지 않는다. 생성을 바깥으로 끌어내라. 이것이
"처음엔 애니메이션되고 그다음엔 절대 안 된다"의 단연 가장 흔한 원인이며, 모든 선언형 UI 시스템에서 똑같은 모양을
하고 있다.

**명목상의 시작값에서 재타깃하고 있다.** 애니메이션이 진행 중에 다시 트리거되면 새 애니메이션은 선언된
시작값이 아니라 **현재** 값에서 시작해야 한다. 현재 값을 먼저 읽어라. 요소가 A와 B 사이 어딘가에 있는데
"A에서 B로 애니메이션"이라고 말하는 것은 무엇이든 A로 되튀고, 그 되튐은 정확히 사용자가 행동한 순간에 일어난다.

**속도가 이어지지 않는다.** 이건 Tier 2 동작이고(`SKILL.md` §2) 버그가 아니라 없는 기능이다. 빠져나갈 길은
세 가지, 순서대로다.

- 실제로 제스처 기반인 인터랙션에 대해서만 spring을 직접 적분하라 — `spring.md` §3.
- `b ≤ 0.15`를 유지해 속도 0에서의 재시작이 이어지는 움직임과 눈에 띄게 다르지 않게 하라.
- 재트리거 가능한 애니메이션은 `dur ≤ 0.2s`로 유지하라. 재시작이 눈에 띄는 문턱 아래다.

**파라미터 체계를 섞지 마라.** 런타임이 duration과 stiffness를 둘 다 받는다면, 한쪽을 설정하면 보통 다른
쪽이 조용히 무력화된다. 어휘 하나를 골라(`Dv`/`b`, 변환은 경계에서) 다른 쪽은 절대 설정하지 마라.

## 3. 리플로우와 공유 요소 애니메이션

**아무 일도 안 일어난다:**

- **그 요소 타입은 transform될 수 없다.** 인라인 텍스트 박스, 일부 레이아웃 관리 컨테이너, 그리고 많은 2D UI
  노드는 transform을 통째로 무시한다. transform 가능한 요소로 바꿔라.
- **레이아웃이 바뀌었다고 시스템에 알린 게 없다.** 리플로우 애니메이션은 *변경 전*과 *변경 후* 측정을 비교해서
  동작하고, 그 비교를 촉발하는 무언가가 있어야 한다. 시스템의 업데이트 사이클을 우회하는 변경은 비교를 만들지
  않고, 따라서 애니메이션도 없다.
- **두 요소가 서로의 레이아웃에 영향을 주는데 따로 갱신된다.** 같은 패스에서 측정되어야 한다. 아니면 한쪽이
  다른 쪽이 아직 비우지 않은 자리로 애니메이션한다.

**레이아웃은 애니메이션 시스템이 아니라 레이아웃으로 구동하라.** 애니메이션으로 크기를 설정하면서 *동시에*
리플로우 시스템이 같은 크기를 애니메이션하게 두는 것은 두 시스템이 한 숫자를 놓고 싸우는 것이다. 레이아웃은 즉시
바뀌게 하고, 시각적 차이는 리플로우 메커니즘이 애니메이션하게 하라.

**콘텐츠 늘어남(scale 왜곡).** scale로 애니메이션되는 rect는 그 안의 모든 것을 왜곡한다. 텍스트가 늘어나고,
모서리 반경이 타원이 되고, 테두리 두께가 변한다. 해결책, 선호 순서대로:

- 직계 자식들을 역수 배율로 역스케일하라.
- 종횡비가 바뀌는 요소(이미지, 텍스트 블록)는 **위치만** 애니메이션하고 크기는 즉시 바뀌게 하라.
- **모서리 반경과 그림자는 애니메이션 시스템이 볼 수 있는 값이어야** 보정할 수 있다. 스타일시트나 정적 에셋에
  파묻힌 반경은 역스케일할 수 없다.
- 테두리는 완벽하게 보정할 수 없다. 1픽셀 하한이 있다. 대신 패딩을 준 부모를 테두리로 써라.

**스크롤 컨테이너 안이나 고정 위치 레이어 안에서는**, 그 컨테이너에 대해 시스템에 알려 주지 않는 한 변경 전/후
측정이 서로 다른 좌표계에서 이뤄진다. 두 경우 모두 대개 명시적인 opt-in이 필요하다.

**스크롤 중 페이지 떨림**은 거의 언제나 스크롤바나 안전 영역 인셋이 나타났다 사라지면서 콘텐츠 폭을 바꾸고, 그것이
모든 것에 리플로우 애니메이션을 유발하는 것이다. 그 여백을 영구적으로 확보해 둬라.

**좌표에 관한 메모:** **부모 기준** 위치를 계산하는 리플로우 메커니즘은 지연된 자식을 움직이는 부모에 붙여 둔다.
**페이지 절대** 위치를 계산하는 쪽은 자식을 뒤에 남긴다. 자식 전환이 부모에게서 떨어져 나온 것처럼 보인다면
이유는 이것이다.

## 4. 성능

**언제나 안전**: transform(translate / scale / rotate), opacity
**페인트 계층 — 측정하라**: 그림자, 모서리 반경, 배경색, 필터
**레이아웃 계층 — 피하라**: width, height, top, left, margin, padding, border width

보편적인 대체법: **비싼 속성을 애니메이션하지 말고, 그 속성의 미리 렌더된 두 상태를 크로스페이드하라.** 블러된
그림자는 불투명도가 애니메이션되는 겹친 오버레이가 된다. 모서리 반경은 마스크 두 개가 된다. 배경 블러는 미리 블러한
사본 두 개가 된다. 메모리를 쓰고 프레임을 산다 — `contrast.md` §6.

클립이나 마스크를 쓸 수 있는 곳에서는 대개 그것이 대체하는 속성보다 싸다. 둥근 rect로 클리핑하는 것이 반경을
애니메이션하는 것보다 낫고, 리빌을 클리핑하는 것이 높이를 애니메이션하는 것보다 낫다.

**레이어 힌트는 아껴 써라.** "이걸 자기 레이어로 승격하라"는 힌트 하나하나가 GPU 메모리를 먹고, 그것으로 가득 찬
페이지는 하나도 없는 페이지보다 느리다. 측정해 본 요소에만 붙여라.

**텍스트가 비싼 경우다.** 텍스트를 조각으로 쪼개면 객체 수가 *한 번* 불어나는데 그건 괜찮다. 매 프레임 텍스트
내용을 다시 쓰면 **계속되는** 텍스트 레이아웃이 유발되는데 그건 안 괜찮다. 최종 크기를 미리 확보하고, 스크램블
효과에는 고정 폭 글꼴을 써서 박스가 다시 측정되지 않게 하라. **글자별 블러는 특정한 함정이다.** 작은 레이어가
잔뜩 생기고 각각이 블러 반경만큼 부풀어 심하게 겹치며, 블록 전체에 블러 하나 거는 것보다 훨씬 비싸다.

## 5. 스크롤

- 스크롤 입력은 이산적이다. 곧장 transform에 묶으면 계단 현상이 생긴다. 언제나 spring으로 스무딩하라 —
  `feel.md` §7.
- **그 spring을 현재 스크롤 값으로 초기화하라.** 아니면 로드할 때 화면이 맨 위에서 훑고 내려온다. 이건 개발
  중에는 재현되지 않기 때문에 — 이미 페이지 맨 위에 있으니까 — 끊임없이 프로덕션까지 나간다.
- 고정은 플랫폼의 네이티브 sticky 메커니즘으로 하고, 스크롤 핸들러에서 위치를 써넣지 마라. 핸들러로 구동하는
  고정은 컴포지터보다 한 프레임 뒤처지고 눈에 띄게 떨린다.
- 스크롤 트리거 애니메이션에는 명시적인 **1회 발화** 플래그와 명시적인 **임계값**(~30% 보일 때)이 필요하다.
  두 기본값 모두 대개 틀렸다.
- "진행률"이 무엇을 뜻하는지 정확히 하라. 대부분의 스크롤 API는 그 범위를 위치 쌍 두 개로 — 대상 위의 한 점과
  컨테이너 위의 한 점으로 — 표현하는데, 그 짝을 거꾸로 잡으면 요소가 화면에 오기도 전에 끝나 있는 애니메이션이나
  영원히 완료되지 않는 애니메이션을 얻는다.

## 6. 제스처와 좌표계

**드래그가 포인터를 따라가지 않는다** → 조상 요소가 transform이나 scale을 지니고 있어서 포인터 좌표와 요소
좌표가 서로 다른 공간에 있다. 포인터 델타를 누적 배율로 나누거나, 쓰기 전에 포인터 위치를 요소의 로컬 공간으로
변환하라. 같은 원인이 scale된 부모 안의 리플로우 애니메이션도 망가뜨린다.

**터치 기기에서 호버가 "박힌다"** → 터치 입력이 짝이 되는 이탈 이벤트가 없는 호버 이벤트를 합성한다. 플랫폼에
걸러진 호버 신호가 있으면 그것을 쓰고, 없으면 touch-end에서 직접 호버 상태를 지우고 "진짜 포인터가 있는
기기인가" 질의로 호버 효과를 감싸라.

**터치에서 드래그가 스크롤과 싸운다** → 제스처가 시작되기 전에 어느 축을 당신이 소유하는지 플랫폼에 알려 줘야
한다. 미리 선언하라. 첫 move 이벤트가 온 뒤에 결정하는 것은 언제나 너무 늦다. 스크롤이 이미 시작됐기 때문이다.

**자식의 탭이 부모 제스처에 삼켜진다** → 제스처 시스템은 흔히 처리를 입력 패스의 끝으로 미루는데, 그 말은
제스처 콜백 안에서 전파를 멈추는 것이 너무 늦다는 뜻이다. 원시 pointer-down에서 멈추거나, 시스템이 제공하는
"이 제스처를 전파하지 마라" 옵션을 써라.

**드래그가 끝날 때 탭이 발화한다** → 포인터가 대략 3px 넘게 움직이면 탭을 취소하라. 대부분의 시스템이 알아서
해 주지만 확인하라. 실패하면 사용자가 카드를 드래그하다가 실수로 여는 결과가 나온다.

**이미지를 드래그하면 고스트가 생긴다** → 플랫폼 자체의 드래그 앤 드롭이 당신 것과 경쟁하고 있다. 그 요소에서
꺼라.

## 7. 상태, 콜백, 생명주기

**애니메이션 완료 콜백에 실제 로직을 절대 매달지 마라.** 애니메이션이 인터럽트되거나, 취소되거나, reduced
motion에서 건너뛰어지면 발화하지 않는데 — 셋 다 정상적인 일이다. 상태는 애니메이션을 일으킨 이벤트에서 구동하고,
애니메이션은 표현으로 남겨라. 어림잡는 법: 제품에서 애니메이션을 전부 지워도 모든 로직이 그대로 돌아야 한다.

**애니메이션과 상태는 어긋날 수 있다.** 애니메이션이 "메뉴가 열렸는가"의 진실 원천이라면, 인터럽트된 애니메이션은
당신의 모델에 존재하지 않는 상태에 당신을 남겨 둔다. 불리언을 유지하고, 거기를 향해 애니메이션하라.

**업데이트마다 새 객체를 만드는 것을 조심하라.** 업데이트할 때마다 새로 만든 설정 객체를 넘기면 동등성 검사가
실패하고, 그 결과 애니메이션이 계속 다시 재생되거나 아무 소득 없이 비교 비용만 든다. 바깥으로 끌어내거나,
메모이즈하거나, 토큰으로 이름 붙여라.
