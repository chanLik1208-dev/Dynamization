# errata.md — 이 팩이 불러들이는 실수들

`pitfalls.md`는 무언가가 눈에 띄게 망가졌고 증상을 찾아볼 때 쓰는 파일이다. **이 파일은 아무것도 망가져 보이지
않을 때를 위한 것이다.**

아래 모든 항목은 해당 장을 읽었고 그대로 따르던 사람이 저지른 실수다. 그게 핵심이다. 이것들은 지식의 실패가
아니라 검증의 실패다. 어느 것도 예외를 던지지 않는다. 어느 것도 경고를 남기지 않는다. 대부분은 그대로 출시된다.

쓰기 전에 이걸 읽고, 다 됐다고 말하기 전에 한 번 더 읽어라.

---

## 사용법

각 항목은 **조용한 증상**부터 말한다. 당신이 얻을 수 있는 게 그것뿐이기 때문이다. 그다음 틀린 코드, 그다음 유능한
구현자가 그래도 그렇게 쓰는 이유, 그다음 해결, 그다음 **실제로 실행할 수 있는 확인법 하나**.

하중을 받는 부분은 확인법이다. 검증할 수 없는 규칙은 결국 어기게 될 규칙이다.

## A. 장을 따랐는데, 환경이 그걸 먹어 버렸다

### A1. 클리핑하는 조상이 미리 렌더한 그림자를 없앤다

**조용한 증상:** 호버할 때 위치는 바뀌는데 엘리베이션이 끝내 도착하지 않는다. `contrast.md` §2가 레이어링
*전부*를 그림자에 싣는 라이트 테마에서는, 호버가 결국 움직임만 지니게 된다. 그건 정확히 `SKILL.md` §5가
경고하는 절반짜리 표현이다.

```css
/* ❌ */
.card { border-radius: 4px; overflow: hidden; box-shadow: var(--e2); }
.card::after { inset: 0; box-shadow: var(--e3); opacity: 0; transition: opacity .13s; }
.card:hover::after { opacity: 1; }
```

**왜 이렇게 쓰게 되는가:** `contrast.md` §6은 `box-shadow`를 애니메이션하지 말고 미리 렌더한 그림자를
크로스페이드하라고 말하고, 그 조언은 맞다. 별개로, 위쪽에 이미지가 있는 둥근 카드는 모서리를 잘라야 하고 카드에
`overflow: hidden`을 거는 것이 반사적인 대응이다. 두 결정 모두 각자로는 옳다. 그런데 그림자는 요소 박스
*바깥*에 그려지므로 클립이 그것을 지운다. 그것도 조용히 지운다. 아무도 볼 수 없는 레이어 위에서 transition이
계속 돌고 있기 때문이다.

```css
/* ✅ clip the thing that needs clipping, not the thing casting the shadow */
.card { border-radius: 4px; box-shadow: var(--e2); }          /* no overflow here */
.card .media { border-radius: 3px 3px 0 0; overflow: hidden; }
```

**확인법:** 요소에 호버하고 카드가 아니라 *그림자*를 봐라. 그림자가 변하는 게 보이지 않는다면 조상들을 거슬러
올라가며 `overflow: hidden`, `clip-path`, 또는 `CanvasGroup` 같은 컴포지팅 래퍼를 찾아라. `outline-offset`으로
그린 포커스 링에도 같은 함정이 적용된다.

### A2. 구워 낸 spring을 `Dv`만큼 재생하면 빠르게 돈다

**조용한 증상:** 움직임의 형태는 맞는데 서두르는 것으로 읽히고, 오버슈트가 잦아드는 게 아니라 툭 끊긴다.

```css
/* ❌ the curve is 0.32s long; the clock says 0.3s */
transition: translate .3s var(--spring-enter);
```

**왜 이렇게 쓰게 되는가:** 토큰 표의 다른 모든 행이 지속 시간이므로 `spring(0.3, 0.15)`도 "0.3초"로 읽힌다.
아니다. `Dv`는 *시각적* 지속 시간 — 움직임이 끝난 것처럼 보이는 지점 — 이고, 구워 낸 곡선은 그 뒤의 잦아드는
꼬리를 필연적으로 포함한다. 두 숫자의 차이는 spring이 튈수록 커진다. `b = 0.4`에서는 꼬리가 전체의 35%다.

```css
/* ✅ */
transition: translate .32s var(--spring-enter);   /* t_settle, from spring.md §4 */
```

**확인법:** `spring.md`의 토큰 표에서 모든 spring은 `Dv`와 `t_settle`을 함께 갖는다. CSS의 지속 시간이
`Dv`와 같다면 틀린 것이다. `linear(` 이징 옆에 있는 `Dv` 값들을 — `.3s`, `.35s`, `.5s` — 지속 시간으로
스타일시트에서 grep해라.

### A3. 클램프된 progress가 조용히 바운스를 없앤다

**조용한 증상:** `b`가 아무 차이도 만들지 않는다. `spring(0.3, 0.15)`와 `spring(0.3, 0.4)`가 똑같아
보이고, 그래서 바운스는 너무 미묘해서 의미가 없다고 결론짓고 쓰기를 그만둔다.

**왜 이렇게 쓰게 되는가:** 샘플링은 제대로 했는데, 런타임이 `0–1` 바깥의 이징 값을 거부하거나 클램프한다.
CSS `linear()`는 받아들이지만, enum 기반이나 곡선 에셋 기반 시스템 상당수는 그렇지 않고, 오류 대신 클램프한다.

**해결:** 자기가 어느 쪽에 있는지 한 번 알아내서 어댑터에 적어 둬라. progress가 클램프된다면 구워 낸 곡선으로는
`b > 0`을 쓸 수 없다. spring을 직접 적분하거나(`spring.md` §3), `b = 0`을 받아들이고 생동감은 다중 속성
규칙에서 가져와라.

**확인법:** 피크가 `1.094`인 `spring(0.3, 0.4)`를 구워서 400px translate에 적용해 봐라. 요소가 400px을
절대 넘어가지 않는다면 progress가 클램프되고 있는 것이다.

### A4. transition을 호버 상태에 걸어서 떠날 때가 즉각적이다

**조용한 증상:** 호버로 들어갈 때는 부드러운데 떠날 때는 툭 끊긴다. 인터랙션 절반은 괜찮게 느껴지고 나머지 절반은
왜 싸구려 같은지 말할 수 없다.

```css
/* ❌ */
.card:hover { translate: 0 -4px; transition: translate .2s; }
```

**왜 이렇게 쓰게 되는가:** 자연스럽게 읽히고 — "호버하면 위로 올라가는데 0.2초 걸림" — 당신이 테스트하던 방향에서는
동작한다. 그 선언은 셀렉터가 매치되는 동안에만 존재하므로, 호버를 벗어날 때는 실행할 transition이 없다.

```css
/* ✅ the transition belongs to the resting state */
.card { transition: translate var(--t-micro); }
.card:hover { translate: 0 -4px; }
```

**확인법:** 포인터를 *멀리* 옮기고 봐라. 언제나 모든 상태의 등장이 아니라 퇴장을 테스트하라. 이건 `feel.md` §5를
당신 자신의 테스트에 적용한 것이고, A4와 A5와 C1을 한꺼번에 잡아낸다.

---

### A5. 이전 값이 없어서 아무것도 등장 애니메이션되지 않는다

**조용한 증상:** 요소가 그냥 나타난다. 오류도, 반쯤 재생된 애니메이션도 없다.

**왜 이렇게 쓰게 되는가:** transition은 계산된 두 값 사이를 보간하는데, 방금 삽입된 요소 — 또는 `display: none`이던
요소 — 에는 떠날 첫 값이 없다. 선언은 멀쩡하다. 할 일이 없을 뿐이다.

**해결:** CSS에서는 `@starting-style`과 `transition-behavior: allow-discrete`
(`adapters/css.md`). 스크립트에서는 시작값을 설정하고 리플로우를 강제한 뒤 최종값을 설정하라. 아무 일도 안 하는
것처럼 보이지만 그렇지 않은 `void el.offsetWidth` 줄이 그것이다. 그런 메커니즘이 없는 런타임에서는 시작값으로
마운트하고 다음 프레임에 바꿔라.

**확인법:** 등장 애니메이션에 한 프레임 전에는 존재하지 않던 요소가 관여한다면 저 셋 중 하나가 필요하다. 네 번째
선택지는 없다.

---

### A6. 아직 투명한 컨테이너 안에서 애니메이션이 재생된다

**조용한 증상:** 분명히 실행되는 효과 — 클래스가 붙는 것도 보이고, 타이밍도 맞고, 중간에 찍은 스크린샷에도
나온다 — 인데 어떤 독자도 본 적이 없다. 그것을 담고 있는 것이 보이게 될 즈음에는 이미 끝나 있다.

**왜 이렇게 쓰게 되는가:** 몇 주 간격으로 쓴 스크롤 옵저버 둘, 각각만 놓고 보면 맞다. 섹션은 한 임계값에서
페이드인하고, 그 안의 요소는 다른 임계값에서 애니메이션한다. 어느 쪽 코드도 상대를 언급하지 않고, 버그는 둘이
겹치는 곳에서만 나타난다 — 그래서 페이드하는 조상이 없는 첫 화면의 요소는 완벽하게 동작하고, 그게 테스트
케이스로 쓰인다.

**해결:** 순서를 매겨라. 컨테이너의 등장이 먼저 시작하고, 내용은 컨테이너가 실제로 화면에 올라와 있을 만큼의
오프셋을 두고 뒤따른다. 부모/자식 오케스트레이션이 있는 런타임에서는 이것이 `beforeChildren`의
용도다(`feel.md` §6). 없다면 딜레이 하나면 된다.

**확인법:** 모든 등장 애니메이션에 대해, 그 순간 조상들이 무엇을 하고 있는지 물어라. 그중 하나라도 페이드
중이거나 스케일 중이거나 아직 opacity 0이라면 이 버그다. **애니메이션은 페이지에서 마침 편했던 첫 자리가
아니라, 실제로 출시될 자리에서 테스트하라.**

### A7. 줄바꿈된 구절은 결코 만족시킬 수 없는 임계값

**조용한 증상:** 효과가 어떤 요소에서는 발동하고 어떤 요소에서는 안 된다. 처음에는 아무 패턴도 보이지 않는다 —
그리고 실패하는 쪽은 더 긴 것들이다.

```js
/* ❌ */
new IntersectionObserver(fn, { threshold: 0.5 }).observe(inlinePhrase)
```

**왜 이렇게 쓰게 되는가:** `0.5`는 반사적으로 쓰는 값이고, 블록에는 맞다. 하지만 두 줄에 걸쳐 줄바꿈된 인라인
요소의 바운딩 박스는 첫 줄 조각의 시작부터 둘째 줄 조각의 끝까지를 아우르고 — 그 박스의 대부분은 두 줄 조각
옆의 빈 여백이다. 관측되는 비율은 그 박스를 기준으로 계산되므로, 구절이 화면에 통째로 들어와 있어도 요청한
임계값에는 끝내 도달하지 못한다.

**해결:** 인라인 대상에는 낮은 임계값을 — `0.1–0.25` — 쓰거나, 대신 블록 레벨 래퍼를 관측하라. 그리고 발동하지
않았을 때의 결과가 보이지 않는 콘텐츠인 곳(§A7 바로 위의 이웃)에는 타임아웃 가드를 더하라.

**확인법:** 테스트 구절 하나를 줄바꿈될 만큼 길게 만들어라. 거의 아무도 하지 않고, 그래서 이게 리뷰를 통과해
살아남는다.

### A8. 사용자 에이전트 스타일시트에 의견이 있었는데 당신이 덮어쓰지 않았다

**조용한 증상:** 당신 팔레트 어디에도 없는 색이 나타난다. 노란색이라고는 하나도 없는 제품에서 하이라이트가
노랗게 나오고, 링크에는 부탁한 적 없는 밑줄이 남아 있고, 컨트롤 하나가 당신의 타입 스택을 무시한다.

```css
/* ❌ 틴트 아래에 노란색이 아직 그대로 있다 */
mark.fs {
  background-image: linear-gradient(var(--hl), var(--hl));
}
```

**왜 이렇게 쓰게 되는가:** 당신은 당신이 생각하던 속성을 설정했다. 그런데 브라우저는 같은 자리에 그리는
*다른* 속성을 이미 설정해 둔 상태였다. 당신의 `background-image` 밑의 `background-color`, 당신의
`color` 옆의 `text-decoration`, 상속되지 않는 폼 컨트롤의 `font`. 당신의 선언은 맞고 자기 캐스케이드에서
이기기도 한다. 다만 그게 표면 전체가 아닐 뿐이다.

```css
/* ✅ */
mark.fs {
  background-color: transparent;
  background-image: linear-gradient(var(--hl), var(--hl));
}
```

**확인법:** 네이티브 시맨틱을 지닌 요소에 스타일을 입혔다면 — `mark`, `button`, `input`, `fieldset`,
`summary`, `dialog`, `progress`, `a` — 당신 스타일을 끈 채로 한 번 봐라. 거기서 보이는 것이 당신이 위에
덧칠하고 있는 것이고, 그중 당신이 명시적으로 이름 대지 않은 부분은 전부 아직 밑에 남아 있다.

### A9. 뷰포트 단위로 크기를 잡은 디스플레이 타입을 라틴 문자로 맞췄다

**조용한 증상:** 영어에서는 맞는데 중국어·일본어·한국어에서는 무너지는 헤드라인. 두 글자 만에 줄이 바뀌거나,
쪼개면 안 되는 단어 한가운데서 끊긴다. 넘치지는 않으니 스크린샷에서는 딱히 망가져 보이지 않는다. 그냥 성의
없어 보일 뿐이다.

```css
/* ❌ 라틴 문자 헤드라인을 놓고 눈대중으로 고른 값 */
h1 { font-size: clamp(46px, 8vw, 92px); }
```

**왜 이렇게 쓰게 되는가:** 헤딩에 영어를 넣어 둔 채로 창을 끌면서 뷰포트 계수를 고르기 때문이다. 라틴 문자는
자형이 좁고 줄이 공백에서 끊긴다 — 크기가 살짝만 커도 단어가 흉하게 넘어가는 것으로 즉시 드러난다. CJK에는
둘 다 없다. 모든 글자가 1em 폭이고, 어느 두 글자 사이에서든 줄이 끊길 수 있다. 너무 크다고 눈에 띄는
줄바꿈이 생기지 않는다. 임의의 줄바꿈이 생길 뿐이고, 그건 여전히 한 줄의 텍스트처럼 보이기 때문에 리뷰를
통과해 살아남는다.

**해결:** CJK 디스플레이 타입은 당신이 도달한 라틴 설정보다 대략 25–35% 작게 잡고, `clamp()` 최댓값은
**그 헤드라인이 차지하게 될 가장 좁은 칼럼**을 기준으로 골라라. 장식용으로 비워 둔 여백까지 포함해서
(`contrast.md` §8이 하나 비워 두는 것을 규칙으로 삼고, 여기서 칼럼을 좁힌 게 바로 그 비워 둠이다).

**확인법:** 모든 `clamp()` 헤딩을 각 브레이크포인트 바로 위 폭에서, 당신이 출시하는 언어 중 자형이 가장 넓은
언어로 봐라. 당신 창 크기에서 보지 말고, 영어로도 보지 마라.

## B. 이 팩이 대놓고 말한 규칙을 어겼다

### B1. 레이아웃 속성으로 무언가를 움직이기

**조용한 증상:** 형태는 멀쩡해 보이는 움직임인데 중급 사양 휴대폰에서 프레임이 떨어지고, 당신 기기에서는 괜찮다.

```js
/* ❌ — and this was written by someone implementing this very pack */
flier.style.transition = "left .32s var(--spring), top .32s var(--spring), width .32s, height .32s";
flier.style.left = to.left + "px";
```

**왜 이렇게 쓰게 되는가:** `getBoundingClientRect()`에서 얻은 사각형 두 개가 있고, 그것들은
`left`/`top`/`width`/`height`로 표현되어 있다. 이미 손에 쥔 숫자를 애니메이션하는 것이 측정에서 움직임으로
가는 가장 짧은 길이고, 결과의 형태도 맞으니 다시 들여다볼 계기가 없다.

```js
/* ✅ place it at the destination, move it with a transform */
flier.style.left = to.left + "px";
flier.style.top = to.top + "px";
flier.style.width = to.width + "px";
flier.style.height = to.height + "px";
flier.style.translate = (from.left - to.left) + "px " + (from.top - to.top) + "px";
flier.style.scale = from.width / to.width;
/* next frame: animate both back to identity */
```

**확인법:** 당신이 쓴 모든 애니메이션에서 `left`, `top`, `width`, `height`, `margin`, `padding`을
grep해라. 히트 하나하나에 이유가 필요하다. `feel.md` §4의 측정-역변환 절차는 그 답이 언제나 transform이
되도록 존재한다.

---

### B2. 하나의 사건, 하나의 속성

**조용한 증상:** 인터랙션이 반응은 하는데 그게 무슨 뜻인지 아무도 말해 주지 못한다. 더 이상의 설명 없이 "싸구려
같다"가 보통의 보고 내용이다.

**왜 이렇게 쓰게 되는가:** 속성이 저마다 다른 시점에 추가된다. 움직임은 컴포넌트를 만들 때 들어가고, 그림자는 디자인
리뷰 코멘트이고, 서피스 변화는 리팩터링 중에 사라진다. 어느 커밋도 혼자서는 틀려 보이지 않는다.

**해결:** `SKILL.md` §3.5의 행들을 메뉴가 아니라 최소치로 다뤄라. 리프트는 변위 **그리고** 더 크고 부드러운
그림자 **그리고** 더 밝은 서피스다. 프레스는 scale 축소 **그리고** 더 좁아진 그림자 **그리고** 어두워짐이다.

**확인법:** 인터랙션당 바뀌는 속성 개수를 세라. 리프트나 프레스에서 셋 미만이면 미완성이다. 그리고 그 셋 중 하나가
그림자라면 A1의 확인법을 다시 돌려라. 그림자가 조용히 사라지는 곳이 거기다.

---

### B3. 대칭적인 퇴장

**조용한 증상:** 인터페이스가 전반적으로 살짝 굼뜨게 느껴지는데, 딱 짚어낼 만한 느린 순간은 없다.

**왜 이렇게 쓰게 되는가:** 퇴장은 대개 등장을 거울처럼 뒤집어 쓴다. 편집이 두 번이 아니라 한 번이면 되니까. 그리고
그건 *틀린* 게 아니다. 그냥 40% 너무 길고, 필요한 거리의 두 배를 지나갈 뿐이다.

**해결:** 퇴장은 등장 지속 시간의 `0.5–0.7×`로, 거리는 절반 이하로, curve는 `in`.

**확인법:** 토큰 세트에서 모든 퇴장 지속 시간을 찾아 그 등장과 비교하라. 2분짜리 감사이고, 제품 전체의 느낌을
바꾼다.

---

### B4. 두 가지 spring 어휘 섞어 쓰기

**조용한 증상:** 파라미터 중 하나가 아무 일도 안 한다. `bounce`를 바꿔도 차이가 없어서 값이 너무 작은가 보다 하고
뭔가 움직일 때까지 밀어붙인다.

```js
/* ❌ */
{ type: "spring", visualDuration: 0.3, bounce: 0.2, stiffness: 400 }
```

**왜 이렇게 쓰게 되는가:** `stiffness`로 쓰인 spring을 물려받았고, 느낌을 조정하고 싶어서 당신이 이해하는
파라미터에 손을 뻗었다. 옛 것은 그대로 둔 채로. 대부분의 구현은 한쪽 체계를 조용히 무시하는 방식으로 이 상황을
정리한다.

**해결:** 프로젝트당 어휘 하나. `Dv`/`b`를 선호하고, 변환은 경계에서 `spring.md` §2로 하라.

**확인법:** `stiffness`와 `damping`을 grep해라. 모든 히트는 변환 함수 안에 있어야 하고, 그 밖에는 없어야
한다.

---

### B5. 숏핸드 하나, 타이밍 함수 하나, 그리고 당신이 생각하지 않고 있던 모든 구간

**조용한 증상:** 가운데는 맞는데 끝이 뚝 멈추는 다단계 애니메이션. 독자들은 "페이드가 이상하다"고 말하고 그
이상은 말하지 못한다. 잘못된 구간이 아무도 보지 않는 구간이기 때문이다.

```css
/* ❌ 그것을 덮어쓴 키프레임 하나를 빼면 모든 구간이 linear */
animation: first-sight 1s linear both;
@keyframes first-sight {
  0%   { …; animation-timing-function: cubic-bezier(.25,.1,.35,1); }
  30%  { … }
  60%  { … }
  100% { … }
}
```

**왜 이렇게 쓰게 되는가:** 숏핸드는 타이밍 함수를 *하나* 요구하고, `linear`가 중립적으로 들리는 선택이고,
그다음 당신은 실제로 설계 중인 구간에 이징을 준다. 나머지 모든 구간은 조용히 `linear`를 물려받는다 —
그리고 시작하고 멈추는 무언가에 `linear`를 쓰는 것은 `feel.md` §10이 짚는 안티패턴이다.

```css
/* ✅ 구간을 시작하는 모든 키프레임에 함수를 하나씩 */
0%   { …; animation-timing-function: cubic-bezier(.25,.1,.35,1); }  /* 와이프 */
30%  { …; animation-timing-function: linear; }                      /* 홀드: 아무것도 안 움직임 */
60%  { …; animation-timing-function: cubic-bezier(.25,.1,.35,1); }  /* 잦아듦 */
100% { … }
```

**따로 짚어 둘 것:** 이 팩 자신의 `recipes.md` §26은 그 잦아듦에 `curve out`을 명시했는데, 구현은
`linear`로 출시됐다. **명세가 맞고 코드가 틀렸으며, 어느 툴체인에도 그 둘을 대조하는 것은 없다.** 코드가
지녀야 할 숫자를 문서가 말해 두는 곳이라면, 그 일치는 양쪽을 다 읽는 사람이 지탱하는 것이다. 그러니 그
숫자를 코드 옆 주석에 적어 둬라. 다음 사람이 찾아보러 가지 않아도 눈에 들어오도록.

**확인법:** 키프레임 안의 타이밍 함수 개수를 세라. 구간 경계마다 하나씩, 아니면 숏핸드의 것을 물려받고 있는
것이다 — 그리고 레시피와 코드를 한 번은 나란히 읽어라, 필요하면 소리 내어.

## C. 애니메이션에 로직을 매달았다

### C1. 완료 이벤트에서 노드 제거하기

**조용한 증상:** 보이지 않는 요소들이 트리에 쌓여 클릭을 가로챈다. 빠르게 조작하는 사용자에게만 일어나므로, 당신이
보고 있는 동안에는 재현되지 않는다.

```js
/* ❌ */
el.addEventListener("transitionend", () => el.remove());
```

**왜 이렇게 쓰게 되는가:** 정확히 이 용도로 문서화된 이벤트이고, 당신이 테스트할 때마다 잘 동작한다. 한 번 클릭하고
기다리는 방식으로 테스트하니까.

```js
/* ✅ the animation is presentation; the removal is not */
el.classList.add("leaving");
setTimeout(() => el.remove(), EXIT_MS);
```

**이유:** 완료 이벤트는 애니메이션이 취소되거나, 인터럽트되거나, 교체되거나, reduced motion에서 건너뛰어지면
발화하지 않는다. 그리고 프로미스 기반 API는 그런 경우 *reject*하므로, catch하지 않은 `await`는 노드를 영영
남겨 둔다. 넷 다 예외 상황이 아니라 정상적인 조건이다.

**확인법:** 퇴장을 트리거한 뒤 곧바로 다시 트리거하거나, 진행 중에 되돌려라. 그리고 트리를 살펴봐라. 또한 reduced
motion을 켜고 제거가 여전히 일어나는지 확인하라.

---

### C2. 애니메이션이 진실 원천이다

**조용한 증상:** 인터럽트된 전환 뒤에 열린 것도 닫힌 것도 아닌 메뉴, 그리고 그다음 토글이 엉뚱하게 동작하는 것.

**왜 이렇게 쓰게 되는가:** 시각 상태와 논리 상태가 같은 사실처럼 보이니까, 변수를 하나만 두는 게 좋은 위생처럼
느껴진다.

**해결:** 불리언을 유지하라. 거기를 향해 애니메이션하라. `pitfalls.md` §7의 판별법이 정확하다. **제품에서
애니메이션을 전부 지워도 모든 로직이 그대로 돌아야 한다.**

**확인법:** 모든 지속 시간을 `0.01ms`로 놓고 제품을 써 봐라. 전부 그대로 동작해야 한다. 그다음 `2s`로 놓고
이것저것 인터럽트해 봐라. 답은 같아야 한다.

## D. 검증하지 않은 것을 믿었다

### D1. 기억에서 꺼낸 API 이름

**조용한 증상:** 가드를 씌운 읽기에서는 아무 일도 없다. 가드가 삼켜 버리고 기능은 영구히 꺼진다. 가드 없는
읽기에서는 아무도 지나가지 않는 코드 경로에서 크래시가 난다.

```lua
-- ❌ the guard makes a wrong name indistinguishable from an absent one
local ok = pcall(function() reduced = GuiService.ReducedMotion end)
```

**왜 이렇게 쓰게 되는가:** 이름이 *거의* 맞고, 방어적인 코드는 좋은 습관이다. 둘이 합쳐져서 조용히 부재하는 기능을
만들어 낸다. 가능한 결과 중 최악인데, 처리된 것처럼 보이기 때문이다.

**확인법:** 출시 전에 이름을 당신의 기억이 아니라 플랫폼 자체의 API 목록에서 읽어라. 가드는 *구버전 클라이언트에
없을 수도 있는* 속성을 위한 것이지, 이름을 아는 것의 대체물이 아니다. 가드를 씌운 읽기가 실패하면 조용히 기본값으로
넘어가지 말고 개발 중에 로그를 남겨라.

---

### D2. 문서가 하지 않은 보장을 주장하기

**조용한 증상:** 없다. 누군가 그 주장 위에 뭔가를 만들기 전까지는. 그다음엔 어떤 코드 줄이 아니라 문서의 한 문장으로
거슬러 올라가는 버그가 나온다.

**왜 이렇게 쓰게 되는가:** 어떤 경우를 명백히 *처리해야 할 것 같은* 컴포넌트는 대개 실제로 처리하고, "X를 처리함"이라고
쓰는 게 "X는 직접 검증하라"고 쓰는 것보다 짧다.

**해결:** 문서가 말하는 것을 말하라. 사실이라고 믿지만 출처를 댈 수 없다면 그 말 그대로 적고, 어떻게 확인하는지도
적어라.

**확인법:** 당신이 쓴 것에 담긴 모든 기능 주장에 대해, 그것을 어디서 읽었는지 물어라. "당연히 그럴 것이다"는
출처가 아니다.

---

### D3. 손으로 만들어 낸 숫자

**조용한 증상:** *대충* 맞는 곡선. 애니메이션되고, spring처럼 보이고, 어떤 리뷰어도 읽어서는 잡아낼 수 없는
방식으로 틀려 있다.

**왜 이렇게 쓰게 되는가:** 값 21개짜리 이징 표는 형태만 보고 어림잡을 수 있는 종류의 물건처럼 보이고, 결과는 흘긋
보고 넘어갈 만큼은 그럴듯하다.

**해결:** 계산해라. `spring.md` §4가 감쇠 영역별 닫힌 형태를 준다. 스크립트 열 줄이면 표가 나온다. 그다음
양 끝점과 피크를 발표된 숫자와 대조하라.

**확인법:** 불변식 두 개가 거의 전부를 잡는다. 표는 정확히 `0`에서 시작해 정확히 `1`에서 끝나야 하고, 그 피크는
`spring.md` §1에 있는 해당 `b`의 오버슈트와 일치해야 한다. 돌아오는 길에 1 *아래로* 내려가지 않는 "통통 튀는"
곡선은 spring이 아니다. 손으로 그린 호일 뿐이다.

## E. 문서 자체의 규율

### E1. 런타임 중립 파일에 들어간 라이브러리 식별자

**조용한 증상:** 더 이상 말이 되지 않는 문장 하나, 그리고 자기 런타임에 존재하지 않는 API를 찾아 나선 독자 하나.

> ❌ 안쪽 항목들: `stagger 0.03`, 컨테이너가 `beforeChildren`인 다음에 시작.

**왜 이렇게 쓰게 되는가:** 그 규칙을 특정 구현에서 배웠고, 그 구현이 붙인 이름이 규칙 자체보다 짧다. 주변 문장을
중립적으로 다시 쓸 때 그 식별자는 전문 용어처럼 보이기 때문에 살아남는다.

> ✅ 안쪽 항목들: `stagger 0.03`, 컨테이너가 다 열린 뒤에만 시작 — `feel.md` §6의
> 컨테이너-먼저-자식-나중 규칙이다.

**확인법:** 판단을 다루는 장들에서 특정 라이브러리의 어휘를 grep해라. 어떤 API도 이름 대지 않겠다고 약속하며
시작하는 파일이라면 그것을 증명할 수 있어야 한다.

---

### E2. 엉뚱한 절을 가리키는 상호 참조

**조용한 증상:** 독자가 그 포인터를 따라가 무관한 내용을 발견하고, 조용히 다른 참조들도 믿지 않게 된다.

**확인법:** 당신이 쓴 모든 `§N`에 대해 §N을 열어 봐라. 기계적이고 지루하며, 이 파일에서 적중률이 단연 가장 높은
확인법이다. 상호 참조는 문서를 재구성할 때마다 썩고, 툴체인의 그 무엇도 그걸 알아채지 못한다.
